# AI 陪读 · 设计说明

> 大肥鱼坐在你右边，跟着你读每一章。

---

## 一、它解决了什么问题

课程是 37 份自包含的 HTML 讲义。读的时候总会冒出这些问题：

- 「这段什么意思？」—— 要去搜索引擎查，回来又找不到位置了
- 「为什么这么设计？」—— 没人回答
- 「我真的懂了吗？」—— 没有反馈

通用 AI 聊天框能回答，但它**不知道你在读什么**：每次都要手动粘贴上下文，
而且它给的是通识答案，不是「你这一章」的答案。

陪读面板的差别就一件事：**AI 一直知道你当前的阅读位置**。

## 二、三个关键设计

### 1. 上下文自动注入

打开任何文件时，面板立刻知道：

| 上下文 | 来源 |
|---|---|
| 章节标题 | 从 `roadmap.js` 的课时数据里按路径反查（拿的是中文正式标题） |
| 所在小节 | 读取当前视口内最近的 `h1/h2/h3` |
| 选中的文字 | 监听选区，取选中段落 |
| 本章正文 | 需要「总结/出题」时才抽取，截断到 9000 字 |
| 阅读进度 | 已读章节数 |

这些会拼进**系统提示词**，所以模型开口就知道你在第 19 章、正看着哪一段。

```python
def build_system_prompt(ctx):
    lines = [
        "你是「大肥鱼」，一只陪学生读书的助教鱼。",
        "【当前阅读上下文】",
        "· 章节：第 19 章 · Agentic Workflow 设计模式",
        "· 所在小节：设计模式的执行流程",
        "【学生刚选中的原文】",
        "...",
        "【陪读原则】",
        "1. 回答要紧贴当前章节，不要泛泛而谈。",
        "2. 讲抽象概念一定配具体例子。",
        "4. 不确定的地方直说不知道，绝不编造 API、论文或数据。",
    ]
```

第 4 条是刻意加的 —— 陪读场景里，编造比不知道危害大得多。

### 2. 选中即问

讲义在 iframe 里。因为 sandbox 给了 `allow-same-origin`，
父页面可以直接读 `iframe.contentDocument` —— 这是整个功能的技术前提。

划一段文字 → 上方冒出「🐟 问大肥鱼」→ 点击直接把选中内容带进去问。

坐标要换算：`iframe.getBoundingClientRect()` + `range.getBoundingClientRect()`，
因为冒泡是画在父页面上的。

### 3. 密钥不出本机

```
浏览器 ──POST──> server.py ──Bearer──> LLM API
                    │
                    └─ 写入 _webapp/.ai-config.json（gitignore）
```

- 密钥**只存服务端**，前端永远只拿到掩码（`sk-abc…1234`）
- 走服务端代理还顺手解决了 CORS 和流式转发
- `.ai-config.json` 已加进 `.gitignore`，不会误提交

## 三、流式响应的实现

用 SSE（Server-Sent Events），但因为要 POST，前端用的是 `fetch` + `ReadableStream`，
不是 `EventSource`。

服务端要手动拼 chunked 编码（`BaseHTTPRequestHandler` 不会自动处理）：

```python
self.send_header("Transfer-Encoding", "chunked")
...
handler.wfile.write(b"%x\r\n" % len(data))   # 16 进制长度
handler.wfile.write(data)
handler.wfile.write(b"\r\n")
...
handler.wfile.write(b"0\r\n\r\n")            # 结束
```

事件格式做了**归一化**，不把上游的 OpenAI 格式直接透传：

```json
{"type": "delta", "text": "你"}
{"type": "done",  "model": "deepseek-chat"}
{"type": "error", "message": "..."}
```

这样换任何 OpenAI 兼容的服务商，前端都不用改。

**客户端还有个坑**：`onreadystatechange` 在 `readyState===3` 时
`responseText` 是累加的，必须自己记 `lastLen` 做增量；而且一次可能只收到半条 SSE 事件，
所以得用缓冲区等到 `\n\n` 才解析。

## 四、界面

右侧 384px 面板，两个标签：

**对话** —— 消息流 + 快捷指令 + 输入框
- 用户消息蓝色靠右，AI 消息白色靠左（带头像）
- 流式期间只更新那一条气泡的纯文本（不重渲染整个列表，否则会卡）
- 结束后才用 `renderMarkdown` 转成富文本

**本章笔记** —— 跟章节走的纯文本，防抖 400ms 自动存 localStorage

**快捷键**：`Ctrl+J` 开关面板

打开陪读时目录面板会自动收起 —— 两个 236px/384px 的侧栏加一起，
中间正文就没地方了。

## 五、降级策略

| 情况 | 表现 |
|---|---|
| 没配密钥 | 面板照常打开，快捷指令可点，提示去配置 |
| 服务商报错 | SSE 里回 `error` 事件，对话里显示 `> ⚠️ 具体原因` |
| 网络断了 | `xhr.onerror` 兜底，提示检查服务 |
| 没选文字 | 「解释选中的」按钮置灰 |
| 没打开文件 | 快捷指令全部置灰，只能自由问答 |

**演示模式**：配置里选 `mock` 预设，不联网返回固定样例 ——
用来验证界面和流式链路是否打通，也方便别人克隆后先看看效果。

## 六、可配置项

`_webapp/.ai-config.json`：

```json
{
  "preset": "deepseek",
  "base_url": "https://api.deepseek.com/v1",
  "model": "deepseek-chat",
  "api_key": "sk-...",
  "temperature": 0.7,
  "max_tokens": 1600
}
```

预设（界面里下拉切换）：

| 项 | 接口 | 模型 |
|---|---|---|
| DeepSeek | `api.deepseek.com/v1` | `deepseek-chat` |
| 通义千问 | `dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| Kimi | `api.moonshot.cn/v1` | `moonshot-v1-8k` |
| OpenAI | `api.openai.com/v1` | `gpt-4o-mini` |
| Ollama 本地 | `127.0.0.1:11434/v1` | `qwen2.5:7b` |
| 演示模式 | `mock://demo` | — |

任何兼容 OpenAI `/chat/completions` 的服务都能用，改 `base_url` + `model` 即可。

## 七、已知限制

- **上下文只有章节级**：不知道你具体看到了哪一段（除非你选中）
- **不记忆跨章节**：换章节就是新对话（这是刻意的，避免上下文膨胀）
- **对话历史存在 localStorage**：清浏览器数据会丢
- **iframe 选区依赖同源**：如果将来给 iframe 换更严格的 sandbox，选中功能会失效
- **没有 token 计数**：长对话靠「只保留最近 16 条」硬截断
